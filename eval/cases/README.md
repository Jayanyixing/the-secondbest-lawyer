# 基准评测集（可机器判定）

`blind/` 那两批是**盲评**：要人读、要人打分，样本是真实案例，跑一轮成本高。这里补的是另一层——**可机器判定的基准集**：输入固定、断言固定，跑分不需要人，用它守住「已经修好的行为不许回退」。

设计原则只有一条：**每个案例都要有一份金标和一份反例**。金标必须全过，反例必须被拦下；两者都成立才算这个案例有判别力。少了任何一边，断言都可能是空的——金标能过不代表断言咬得住错误，反例被拦也不代表金标写得对。

## 为什么不用真实交付物

真实客户文书即便手工脱敏，也容易残留项目代号、非标金额、专有条款细节，放进 Git 仓库违反「数据与材料边界」。所以这里的输入全部是**合成场景**：场景取自 `references/acceptance-scenarios.md`，事实与金额为虚构，条文取自本地 `data/law.sqlite`（条号与原文可核），案例卡取自 `data/cards.sqlite`（已是脱敏 XXX 案号）。

## 怎么跑

```bash
python3 tools/eval_cases.py                 # 自检：金标全过 + 反例被拦，输出判别力 n/12
python3 tools/eval_cases.py --list          # 列案例
python3 tools/eval_cases.py --case E03      # 只看一个
python3 tools/eval_cases.py --case E03 --answer path/to/answer.md   # 判一份真实产出
```

自检通过的判据是「判别力 12/12」：每个案例都满足金标全过、反例至少被一条断言拦下。任何一条不满足，脚本退出码为 1。

## 断言类型

写在 `*.case.json` 的 `checks` 里，全部零依赖实现在 `tools/eval_cases.py`：

| 类型 | 参数 | 判定 |
|---|---|---|
| `must_include` | `values: [正则…]` | 每条正则都要命中 |
| `must_not_include` | `values: [正则…]` | 每条正则都不许命中 |
| `must_not_affirm` | `values: [词…]` | 不得「肯定地」声称；同一分句内有否定词不算（复用 `affirms_claim`） |
| `max_lines` | `value: n` | 行数上限（考篇幅克制） |
| `case_no_allow` | `values: [案号…]` | 正文出现的案号必须全在白名单内 |
| `lint` | `mode`／`strict`／`contract`／`absent`／`present` | 跑 `citation_lint`，按规则号判 |
| `docgen` | `template`／`input`／`placeholders` | 从 JSON 生成 docx，校验 XML 合法、无 `\x0c`、占位符数一致 |

## 边界（读结果前必看）

- 这 12 个案例**不构成准确率**。它们只覆盖已知的失败模式，是回归网，不是能力评估；能力评估仍看 `eval/README.md` 那两批盲评。
- 断言是启发式的：靠关键词与 lint 规则判定，不读懂论证质量。金标因此写得刻意克制（只写能判定的部分），别把它当范文。
- 反例是**同一场景的典型错法**，不是最难的错法。反例被拦只说明这一类错误拦得住。
- 新增案例时，先写反例再写金标：如果反例过不去、金标也过不去，说明断言写的是场景噪声，不是可判定的行为。

## 加一个案例

1. 新建 `E0X-<slug>.case.json`，`case_id` 用 `E0X`；
2. 写 `E0X.gold.md` 与 `E0X.bad.md`；
3. 跑 `python3 tools/eval_cases.py --case E0X`，直到金标全过、反例被拦；
4. 把编号与断言数补进上面的表。
